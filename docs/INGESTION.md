# 从视频和评论中整理积分赛破阵案例

> 本工具不访问 B 站、不会请求网络、更不需要 Cookie；它处理贡献者**合法获得且人工录入**的文字材料。示例完全虚构。不要绕过平台访问限制抓取视频或评论。

## 两个高价值信号

1. **视频标题 + 简介**：只有同时出现明确标识的“防守：三个忍者”与“进攻：三个忍者”时，规则提取器才自动填两队。标题只写“三号百虎”不会假设另外两个忍者任意。
2. **玩家的原评论 + 其下方的回复**：需要连同父评论、回复、各自的 ID 和 `video_owner_id` 保存成同一条证据。属于 UP 本人的回复可生成待审案例；普通用户的回复仅作为未确认线索。UP 回复也不等于实测成功。

仅保留必要的结构化摘要与来源定位，不要在公开仓库保存完整评论树、Cookie、评论者昵称、头像、账号资料或受版权保护的视频全文。评论 ID 是用于回查的定位信息，不要用于画像。

## 如何开始（无需 API）

查看 `examples/demo_evidence.json`，用同样结构新建自己的 `data/inbox/2026-10-xx.json` 文件（已设置 Git 忽略，不会误上传原评论）。手动从可访问的视频页面记录标题、简介、发布日、UP主 ID、相关父评论和 UP 回复。日期和作者身份**不能猜**。

```bash
python scripts/ingest_evidence.py preview data/inbox/2026-10-xx.json --out build/proposals.json
```

程序将识别忍者名称和常见简称，提取明确给出的三人防守、三人进攻，以及原作者写出的跨度百分比。跨度未知时写 `未提供`，分母一直为 `unspecified`，不擅自推断。建议首先检查 `build/proposals.json` 中的 `readyForReview`、`reason` 和 `sourceRef`。

**每条提取结果即使解析完整，也只是候选**。程序不会自动写入 `data/cases.json`。

核对一条候选时，必须打开原始视频，确认站位、评论真实归属、版本和限制；同时查找数据库是否已有相同阵容。候选 ID 在 `build/proposals.json`。对于高确定性（且由视频作者确认）的完整案例：

```bash
python scripts/ingest_evidence.py approve build/proposals.json --id biliv-替换成真实ID --version 2026-10 --confirmed
python scripts/build.py
python -m unittest discover -s tests -v
```

`--confirmed` 是贡献者声明已经核查原始证据，不是自动认证。正式合并仍须经 GitHub PR 审核。审批后新增的记录为 `ready`，只表示**资料完整可检索**，不代表已实测跨战力或确定胜率。

如果解析不完整、未知简称、作者身份无法证实、跨度计算口径不明，停留在候选区手动修正；不要使用猜测填充；缺少关键站位时仅添加到 `data/research-queue.json`。若与现有阵容重复，审批会拒绝直接重复插入，应人工合并证据引用。

## 如何走向批量化

- **第一阶段**：创建博主名单、人工整理 5–10 条视频和评论，确认实际命中率。这个阶段已经具备离线文本解析和入库脚本。
- **第二阶段**：与愿意合作的 UP 主约定数据提交方式，让博主或授权提供方按上述 JSON 提供原始结构化信息，减少人工整理。
- **第三阶段**：仅在数据服务的授权与平台条款允许后，增加受控获取适配器，用 BV 号获取获准访问的元信息、评论楼层和二级回复；适配器输出与上述格式相同的 JSON。采集失败时停下，不绕过验证、限流或权限。

## 输入格式

```json
{
  "video_url": "https://example.org/fictional-video",
  "video_id": "FICTIONAL_ONLY",
  "video_owner_id": "DEMO_UP",
  "published_at": "2026-10-01",
  "title": "视频标题",
  "description": "防守：百蛇、普佩、百虎。进攻：须鼬、创立柱间、天道超。",
  "comments": [
    {
      "comment_id": "root-01",
      "author_id": "PLAYER",
      "text": "百蛇、普佩、百虎怎么破？",
      "replies": [
        {"reply_id": "reply-01", "author_id": "DEMO_UP", "published_at": "2026-10-05", "text": "须鼬、创立柱间、天道超，跨度没测过"}
      ]
    }
  ]
}
```

以上是一段虚构演示，不能作为真实破阵案例。原始评论和回复不能拆开，否则会破坏证据语义。评论 ID / 视频 ID 用来避免同一条问答被重复录入。**视频日期不等于评论回复日期**，单独记录 `replies[].published_at`；没有确切日期时保留为待核线索。

## 质量控制

- 只把完整准确的三对三放入正式数据库；若只明确三号位，不能偷偷补足前两位。
- 保留来源链接、发布时间、楼层定位、获取方式和审核状态。
- “作者说可跨 15%”与“测试成功 15%”是不同的证据，不能等同；战力百分比没有分母时不能用于保底计算。
- 游戏大版本更新后将旧方案标记为待复测或归档，允许一条公式在多个版本分别保留记录。
- 多条来源重复描述相同阵容时，应合并证据而不是无脑统计成多次成功。
